# Custodia Android candidata — 2026-10-22

Continuación de `36933c6fc44cd8055f7a80b10b5568614bc1e3dc` en `feat/android-commercial-runtime`; PR #96 draft apilada sobre la rama de PR #92 draft. Perfil de laboratorio, **sin habilitar producción ni local-security comercial**. No se modifica `main.ts`, DPAPI, SSA, sesiones, permisos, migraciones ni el bloqueo del cajón.

Código nuevo: `AndroidRootCustody` en el host propio genera una clave AES-256-GCM no exportable mediante Android Keystore. Protege una semilla aleatoria de 32 bytes en un sobre privado versionado (magic/IV/tag/ciphertext), AAD ligado al paquete y commit AtomicFile. No crea otra base. Si clave/archivo divergen, falta raíz con secretos previos o falla el tag, rechaza; no elimina claves ni regenera una identidad. No hay fallback de claves derivadas públicas. Backup Android sigue deshabilitado.

La semilla en claro pasa exclusivamente por stdin heredado del proceso Node que arranca el mismo UID, con binario/assets verificados: no env, argv, logs, URL, React ni archivo plano. El entry exige Android, directorio privado y descriptor pipe/socket heredado, lee exactamente 32 bytes antes del control de parada y limpia el buffer. `AndroidKeystoreKeyProvider` implementa el puerto existente, HKDF-SHA256 por contexto exacto y destrucción explícita. En el cierre final, almacén y proveedor del diagnóstico se destruyen **inmediatamente después de comprobar el sello**, antes de abrir la base; no mantienen claves de diagnóstico durante la espera del Service. Es un adapter privilegiado: el constructor no es un verificador de procedencia externa ni autentica una persona. No se expone por transporte.

`EncryptedFileSecretStore` canónico cifra/reabre solo `android-foundation-check`, un valor de diagnóstico sin autoridad. `OS_BOUND` describe la protección en reposo; la semilla y claves derivadas son utilizables en RAM por el proceso confiable. No se afirma Ed25519 no exportable, StrongBox, attestation remota ni defensa frente a compromiso del UID/OS. La raíz local de cifrado no es rootTrustAnchor ni clave central DEVICE_TRUST/SSA. El contexto de este sello es de diagnóstico, **no** el binding de instalación/dispositivo de una identidad comercial. Para ese binding se debe reutilizar deviceIdentityContext y el flujo DeviceEnrollmentService/DeviceEnrollmentActivation/Request/Result existente, con sus verificaciones centrales; no crear un enrollment paralelo.
