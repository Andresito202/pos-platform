## Implementación materializada

El bloque ya implementado en la línea activa contiene:

1. contrato `SESSION_ASSERTION` con estados `ACTIVE | VERIFY_ONLY | REVOKED`, `environment`, vigencia y versión;
2. firma del artefacto operacional bajo un root trust anchor inyectado;
3. persistencia local protegida del artefacto firmado mediante `EncryptedFileSecretStore`, sin claves privadas;
4. resolver que produce el `TrustedSigningKey` consumido por `SessionAssertionVerifier`;
5. configuración explícita del root público y environment, ambos opcionales y obligatoriamente pareados;
6. wiring real de `CommercialComponent`: el mapa ya no se fabrica como `new Map()` incondicionalmente;
7. propagación de la ventana de vigencia de la trust key hasta la verificación de cada SSA, evitando que una clave operacional expirada siga siendo válida solo por permanecer en memoria;
8. pruebas de firma raíz, environment, revocación, expiración y material malformado.

La ausencia de artefacto sigue siendo fail-closed para `session.activate` y no bloquea el arranque de operaciones locales no relacionadas.

La materialización del root en el **entorno real de despliegue** sigue pendiente de evidencia.

## Materialización del caller central — 2026-10-09

Se añadió `SessionTrustBundleFetcher` y se conectó a `apps/pos-local-service/src/main.ts`. Cuando están configurados `POS_CENTRAL_BASE_URL`, `POS_SESSION_TRUST_TRANSPORT_TOKEN_FILE`, `POS_SESSION_TRUST_ROOT_PUBLIC_KEY_PEM` y `POS_SESSION_TRUST_ENVIRONMENT`, el arranque solicita `GET /v1/session-trust` por HTTPS. El fetcher rechaza redirecciones, aplica timeout y limita a 64 KiB durante la lectura del stream antes de parsear y validar el schema; el `SessionTrustKeyStore` valida firma raíz, propósito, environment y generación antes de persistir. El bearer se lee de un archivo de despliegue y nunca se usa como trust anchor. Si falla la distribución, se intenta resolver el bundle local protegido/artefacto de instalación; sin bundle confiable la sesión sigue fail-closed.

Se añadieron pruebas del límite HTTP, rechazo de credenciales malformadas, validación de rutas, instalación de bundle firmado, rechazo de bundle firmado por otra raíz, fallback a trust cache previamente válida, configuración y refresco en vivo de rotación/revocación. El workflow G1.2 ejecuta ahora `config.test.ts`, las pruebas de trust y los E2E de sesión. Estas pruebas todavía requieren ejecución observable en Actions.

## Lo que sigue bloqueado por evidencia/materialización

Todavía no se puede declarar `RUNTIME_VERIFIED` porque faltan:

- el root public key y el token de transporte materializados con permisos correctos en el entorno real de despliegue;
- ejecución observable del servicio con distribución central configurada;
- E2E real que demuestre distribución central, `session.activate`, recuperación tras reinicio y replay;
- evidencia de rotación/revocación a través del endpoint central en runtime;

No se genera una clave raíz local ni se usa `DEVICE_TRUST`, bearer token o clave privada del dispositivo como sustituto.
