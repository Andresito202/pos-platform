# G1.2 — Implementation Gate

Estado: `BLOCKED UNTIL TRUST-PURPOSE DECISION`

## Entrada requerida

La implementación del session bootstrap queda habilitada únicamente cuando exista una decisión ratificada que cierre el propósito criptográfico del emisor de SSA y su distribución al POS.

## Evidencia arquitectónica consolidada

La auditoría del árbol actual confirma que existe maquinaria reutilizable para **verificar** artefactos firmados, pero no existe todavía un mecanismo autorizado que **publique/provisione** las claves de firma de SSA al Local Service.

- `TrustedSigningKey` ya es el modelo consumido por los verificadores de SSA/SAS/licensing.
- `licensing.trusted_signing_keys` ya modela `key_id`, `key_purpose`, `environment`, clave pública, checksum, estado y vigencia.
- El modelo físico exige separación por `key_purpose`; no se encontró un propósito canónico `SESSION_ASSERTION` materializado.
- `SnapshotAcquisitionService` solo adquiere un **Signed Authorization Snapshot** a través de un `SnapshotProvider`; su propio puerto declara que el transporte HTTP productivo todavía no existe. Por tanto, no es una vía existente de distribución de claves de sesión y no debe reutilizarse por analogía sin decisión contractual.
- `CommercialComponent` continúa recibiendo `sessionSigningKeys` por inyección; el runtime productivo mantiene el mapa vacío y, correctamente, queda fail-closed.

Conclusión: **no hay base documental ni código existente suficiente para implementar el bootstrap sin cerrar primero el propósito y la distribución de la trust key de SSA**.

## Paquete de implementación posterior

El cambio autorizado deberá resolver en una sola línea coherente:

1. contrato de propósito de clave de sesión;
2. trust material central y publicación;
3. verificación del artefacto de distribución;
4. almacenamiento local protegido/íntegro;
5. resolver de `TrustedSigningKey`;
6. wiring de `CommercialComponent`;
7. caller reachability de `session.activate`;
8. recuperación después de reinicio;
9. rotación y revocación;
10. pruebas negativas de propósito, firma, binding, expiración y replay;
11. E2E runtime.

## Gates que no se pueden saltar

- No `new Map()` como solución de producción.
- No clave local generada como autoridad.
- No reutilizar `DEVICE_TRUST` para firmar SSA.
- No usar bearer token de transporte como trust anchor.
- No bypass de `SessionAssertionVerifier`.
- No renderer secret exposure.
- No declarar `CALLER_REACHABLE` sin una ruta real desde el runtime.
- No declarar `RUNTIME_VERIFIED` sin ejecución observable.
