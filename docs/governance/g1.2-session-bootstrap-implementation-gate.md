# G1.2 — Implementation Gate

Estado: `IMPLEMENTED_PARTIAL — DISTRIBUTION/CALLER RUNTIME PENDING`

## Autorización

La decisión de propósito y separación fue autorizada para implementación: SSA usa el propósito canónico `SESSION_ASSERTION`, separado de `DEVICE_TRUST`, con clave pública operacional emitida centralmente, vinculada al `environment`, rotatable/revocable y verificada contra un root product-owned fuera de banda. La aprobación no autoriza inventar el root trust anchor ni material criptográfico de producción.

## Implementación materializada

El bloque ya implementado en la línea activa contiene:

1. contrato `SESSION_ASSERTION` con estados `ACTIVE | VERIFY_ONLY | REVOKED`, `environment`, vigencia y versión;
2. firma del artefacto operacional bajo un root trust anchor inyectado;
3. persistencia local protegida del artefacto firmado mediante `EncryptedFileSecretStore`, sin claves privadas;
4. resolver que produce el `TrustedSigningKey` consumido por `SessionAssertionVerifier`;
5. configuración explícita del root público y environment, ambos opcionales y obligatoriamente pareados;
6. wiring real de `CommercialComponent`: el mapa ya no se fabrica como `new Map()` incondicionalmente;
7. propagación de la ventana de vigencia de la trust key hasta la verificación de cada SSA, evitando que una clave operacional expirada siga siendo válida solo por permanecer en memoria;
8. pruebas de firma raíz, environment, revocación, expiración y material malformado.

La ausencia de artefacto sigue siendo fail-closed para `session.activate` y no bloquea el arranque de operaciones locales no relacionadas.

### Estado actual del trust anchor en el repositorio

El repositorio actual **no contiene** `infra/trust/camacho-pos-session-trust-root-public.pem`. Esto es consistente con la política vigente de repositorio, que prohíbe trackear extensiones `.pem` como material sensible. No se debe restaurar ese archivo sólo para satisfacer una referencia documental anterior.

La arquitectura vigente exige que el root público sea material de despliegue/inyección controlada mediante `POS_SESSION_TRUST_ROOT_PUBLIC_KEY_PEM`, mientras que el bundle operacional público puede viajar como artefacto verificable. La materialización del root en el **entorno real de despliegue** sigue pendiente de evidencia.

## Lo que sigue bloqueado por evidencia/materialización

Todavía no se puede declarar `CALLER_REACHABLE` ni `RUNTIME_VERIFIED` porque faltan:

- una fuente real de publicación/entrega del artefacto firmado al Local Service;
- el root public key de producto materializado en el entorno de despliegue real;
- ejecución observable del servicio con artefacto válido;
- caller/E2E que demuestre `session.activate` contra esa trust key después de reinicio;
- evidencia de rotación/revocación en runtime.

No se genera una clave raíz local ni se usa `DEVICE_TRUST`, bearer token o clave privada del dispositivo como sustituto.

## Gates que no se pueden saltar

- No `new Map()` como solución de producción.
- No clave local generada como autoridad.
- No reutilizar `DEVICE_TRUST` para firmar SSA.
- No usar bearer token de transporte como trust anchor.
- No bypass de `SessionAssertionVerifier`.
- No renderer secret exposure.
- No declarar `CALLER_REACHABLE` sin una ruta real desde el runtime.
- No declarar `RUNTIME_VERIFIED` sin ejecución observable.
