# G1.2 — Session trust-purpose decision gap

Estado: `BLOQUEADO POR DECISIÓN DE ARQUITECTURA — NO IMPLEMENTAR`
Fecha: 2026-09-17

## 1. Hallazgo consolidado

La cadena de sesión ya está implementada hasta el punto correcto de consumo:

```text
SignedSessionAssertion
  → SessionAssertionVerifier
  → SessionActivationService
  → SessionAssertionStore
  → CommercialComponent
```

El verifier exige resolver `claims.key_id` contra `ReadonlyMap<string, TrustedSigningKey>` y rechaza una clave desconocida o revocada. `CommercialComponent` actualmente recibe el mapa vacío por defecto.

Esto no es un defecto del verifier ni del contrato SSA. Es una ausencia de provisioning del trust material.

## 2. Contradicción que impide implementar todavía

La documentación existente define un catálogo genérico `licensing.trusted_signing_keys` con:

- `key_id`;
- `key_purpose`;
- `environment`;
- clave pública;
- estado `ACTIVE` / `VERIFY_ONLY` / `REVOKED`;
- rotación/revocación.

También define que las superficies criptográficas deben estar separadas por propósito. Sin embargo, la documentación consultada no fija un `key_purpose` canónico para las SSA ni un flujo que publique ese trust material al POS.

`DEC-012` sí fija una decisión diferente y suficiente para el origen del artefacto: **la SSA es emitida centralmente**. No autoriza al POS local a generar una autoridad de sesión.

Por tanto, estas dos proposiciones NO pueden fusionarse por conveniencia:

1. `TrustedSigningKey` es el mecanismo de verificación local.
2. La clave que firma SSA ya está definida como una clave de propósito sesión.

La primera está implementada; la segunda todavía no está cerrada documentalmente.

## 3. Lo que queda determinado

### 3.1 Emisor de SSA

La autoridad de la SSA es central. El POS local no firma SSA y no crea una confianza de sesión propia.

### 3.2 Material confiado por el POS

El POS necesita solamente la **clave pública** del emisor de SSA para verificar la firma. No necesita ni debe recibir la clave privada del emisor.

### 3.3 Separación de propósito

La clave `DEVICE_TRUST` no puede reutilizarse como clave de firma SSA.

La clave `MASTER_SNAPSHOT` no puede reutilizarse como clave de firma SSA.

La clave de actualización, licencia u otra finalidad tampoco puede convertirse implícitamente en autoridad de sesión.

### 3.4 Lifecycle

La resolución local debe conservar como mínimo `ACTIVE`, `VERIFY_ONLY` y `REVOKED`, porque son los estados que ya entiende `TrustedSigningKey`.

### 3.5 Offline

Una SSA ya emitida puede verificarse offline únicamente si su clave pública de confianza ya está presente y es verificable. La ausencia de esa clave no constituye motivo para aceptar la SSA de otra forma.

## 4. Decisión que falta

Debe cerrarse explícitamente un propósito criptográfico canónico, por ejemplo conceptualmente:

```text
key_purpose = SESSION_ASSERTION
```

El nombre exacto queda pendiente de ratificación; no se debe inventar un literal en código antes de esa decisión.

La decisión debe cubrir simultáneamente:

1. literal canónico de `key_purpose`;
2. autoridad/emisor central;
3. environment binding;
4. cómo se publica/replica la clave pública al POS;
5. cómo se verifica el artefacto que introduce la clave al trust store;
6. persistencia local y atomicidad;
7. rotación `ACTIVE → VERIFY_ONLY → REVOKED`;
8. comportamiento offline;
9. auditoría de aceptación/revocación;
10. E2E que pruebe clave válida, desconocida, revocada y propósito incorrecto.

## 5. Qué NO se hará

- No generar una clave de sesión local al arrancar.
- No convertir `DEVICE_TRUST` en `TrustedSigningKey` de sesión.
- No usar `MASTER_SNAPSHOT` como sustituto.
- No rellenar `sessionSigningKeys` con una clave hardcodeada.
- No modificar `session.activate` para ocultar `SESSION_NOT_BOUND`.
- No modificar Payment/Cash/Sale/Inventory para evitar este bloqueo.
- No declarar Session runtime `VERIFIED` por tests unitarios.

## 6. Relación con Actions / D-3

El bloqueo de GitHub Actions permanece separado en issue #83. La falta de runtime evidence D-3 no justifica inventar el trust material de sesión.

D-3 continúa en estado `RUNTIME VERIFIED: NO` hasta que Actions produzca evidencia observable.

## 7. Entrada a implementación

Una vez ratificado el propósito de clave y su distribución, el siguiente bloque de implementación deberá ser único y completo:

```text
central signing purpose
  → trusted public-key publication
  → local authenticated trust-store persistence
  → runtime resolver
  → CommercialComponent wiring
  → session.activate caller reachability
  → restart/recovery
  → revoked/rotated-key behavior
  → real E2E
```

No se debe implementar una parte que deje otra dependencia de confianza sin resolver.
